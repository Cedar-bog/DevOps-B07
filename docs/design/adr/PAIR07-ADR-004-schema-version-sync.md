# PAIR07-ADR-004：公共 Schema 的版本同步方式

- 状态：Accepted
- 命名空间：`PAIR07-ADR-*` = A07 / B07 双方共同决策
- 日期：2026-09-22
- 关联任务：E2-B07-015（J4）
- 关联文档：`B07-ADR-0002-artifact-passing.md` §版本约定；`contracts/task.schema.json`

## Context

双方共享的字段结构与语义（`task.schema.json` 的公共字段与 `$defs/artifact`、A07 的产物 Schema）属于同一份契约。需要约定的不是「要不要版本号」，而是两件事：

1. **同步流程**：一次 Schema 变更要经过什么步骤才算生效。
2. **由谁递增**：版本号由哪一方提升。

这一步其实**已有答案**：`B07-ADR-0002` §版本约定 原文即「产物引用的字段结构与语义属于共享契约的一部分，变更须同步 `task.schema.json` 的 `schema_version` 并保留已有字段含义；新增可选字段须得到消费者（A07）允许」。本 ADR 不是重新设计，而是把该条文明文固化为流程。

## Decision

**`schema_version` 保持 `const: "1.0"`，把同步写成明文流程。**

流程：

1. 任何公共 Schema 变更 → **发起方先在 backlog / ADR 立项**（记明动机与影响面）。
2. **双方确认**后，在**同一提交内**更新 `schema_version` 与全部受影响的样例。
3. 版本号由**变更发起方**递增。

`task.schema.json` 中 `schema_version` 保持 `const: "1.0"`，不做数值范围匹配。

为什么不用语义化版本（如 `pattern: "^1[.][0-9]+$"` 允许 `1.1`、`1.2`）：那样会让「两边版本不同步」**静默通过** —— 校验器无法从 `1.0` 与 `1.1` 判断某一侧的消费者能否互通，冲突要等到运行时才暴露。E2 规模下两边本就是手工同步，`const` 的价值在于**一旦两侧不一致就立刻报错**。宁可响得吵，不要错得静默。

## Alternatives

- **语义化版本 + 范围匹配 `^1[.][0-9]+$`**：更「正规」，允许小版本滚动。代价是版本不同步时校验静默通过，而 E2 阶段最需要抓住的恰恰是「没同步」。若日后样例数量增长到手工同步不可行，再引入，并同时引入最低版本声明。
- **两侧各自独立版本号**：各自递增、互不约束。产生两处真源，无法判断兼容性，与「同一份共享契约」的定位矛盾。
- **不设版本号**：靠字段的 `required` / `additionalProperties` 隐式约束。字段增减虽能被 `additionalProperties: false` 抓到，但**语义变更**（同名字段含义改变）无从发现，这正是版本号要覆盖的部分。

## Consequences

### 正面

- 版本不同步时立即报错，不静默通过。
- 「谁递增」有明确答案（变更发起方），不存在互相等待或重复递增。
- 流程短（立项 → 确认 → 同一提交更新），与 E2 的手工同步规模匹配。

### 代价与待办

- 每次变更都要求「同一提交内更新样例」，任何一侧漏改样例都会被 `validate.py` 的版本校验直接抓住——这是刻意保留的摩擦。
- 兼容性等级的细粒度声明（如「本次变更向后兼容」）不在此机制内表达，需在立项的 ADR 中人工写明；E2 规模下可接受。
