# PAIR07-ADR-003：错误码前缀分域与按前缀区分的宽容规则

- 状态：Accepted
- 命名空间：`PAIR07-ADR-*` = A07 / B07 双方共同决策
- 日期：2026-09-22
- 关联任务：E2-B07-015（J3）
- 关联文档：`contracts/examples/status_error.json`
- 关联 ADR：`PAIR07-ADR-004`（放宽枚举属共享 Schema 变更）

## Context

双方已就三个错误码达成一致，写入 `job.error`：

| 错误码 | 语义 | 会产生的一方 |
|---|---|---|
| `ENV_3002` | 镜像构建失败 | B07（`DRAFT` 构建）/ A07 |
| `EXEC_4002` | 任务超时 | 双方均可能 |
| `ANALYSIS_5001` | 分析器失败 | A07 |

A07 在 `error-codes.md` 中表示希望在 `ANALYSIS_*` 下细分更多编码，并暂缓把这些细码写入双方共享枚举，改用 `message` / `details` 表达，待 B07 确认。问题因此变成：**A07 新增错误码，是否必须写入双方共享表？**

关键判断是：A07 加码会不会破坏 B07，不取决于「有没有过会」，而取决于「**B07 遇到不认识的码会不会炸**」。把宽容写成契约义务之后，双方就不必为每次加码开会。

但「宽容」不能无条件：B07 自己的负例 fixture `unknown_error_code` 断言 `ENV_9999` **必须被拒绝**（`E2-B07-010` 约束类别 `enum`）。把这两件事调和起来的关键是——**按前缀区分**：共享前缀下的未知码是真实分歧，必须响；A07 专有前缀下的未知码是对方内部细节，必须容忍。

## Decision

**不进同一张表，改为「前缀分域 + 按前缀区分的宽容规则」。**

### 前缀分域

| 前缀 | 归属 | 扩展规则 |
|---|---|---|
| `ENV_*`、`EXEC_*` | 平台共享（B07 也产：DRAFT 构建失败、REPAIR 超时） | 新增须双方确认 |
| `ANALYSIS_*` | A07 专有（分析器内部失败） | A07 可自由扩展 |

### 宽容规则（按前缀区分）

| 消费者遇到 | 处置 | 理由 |
|---|---|---|
| 共享前缀（`ENV_*`/`EXEC_*`）下的未知码 | **拒绝** | 双方都产这些码，出现未协商值意味着契约真的分叉了，必须响得吵 |
| A07 专有前缀（`ANALYSIS_*`）下的未知码 | **容忍**：原样记录、不解析语义、不崩 | 属 A07 内部细分，B07 不消费其语义；容忍后 A07 可自由扩展 |

### B07 侧落地

- `contracts/examples/status_error.json`：`error_codes` 下每项加 `owner`（归属）与 `scope`（`platform` / `a-only`）标注，并新增 `namespaces` 块与 `consumer_tolerance` 说明。
- `contracts/task.schema.json`：`job.error.code` 的 `description` 写明前缀分域与上述宽容规则。**枚举本身暂保持封闭为三个已协商码**——放宽为 `^ANALYSIS_[0-9]{4}$` 属共享 Schema 变更，按 `PAIR07-ADR-004` 须双方确认，B07 不在单方提交中先行修改。

## Alternatives

- **所有错误码进同一张共享表**：语义最集中。但 A07 每加一个 `ANALYSIS_*` 内部细分都要跨组确认，而 B07 根本不消费这些码的语义；把「B07 用不到的码」变成双边阻塞点，成本与收益不成比例。
- **完全不共享错误码**：各自维护。但 `ENV_3002`/`EXEC_4002` 的实际生产者是双方，没有共享定义则同一语义会出现两种拼写，`job.error` 无法跨组解读。
- **无条件容忍所有未知码**：实现最简单，只需反序列化不失败。但这会让共享前缀下的未协商码**静默通过**——A07 若把 `ENV_3002` 拼成 `ENV_3003`，B07 会当成未知码记录而非报错，真正的分歧被吞掉。与「宁可响得吵，不要错得静默」的原则冲突。
- **共享表 + 数字段预留**：例如 `ANALYSIS_5xxx` 预留给 A07，跨段才需确认。与「前缀分域」同源，但把约束压在数字段上不够自描述；前缀字面即表达归属，更直观。

## Consequences

### 正面

- A07 可在 `ANALYSIS_*` 下自由细分，双方无需为每次加码开会。
- 只有跨前缀（影响 B07 也会产生的码）才需确认，跨组成本降到最低。
- 与既有负例 fixture `unknown_error_code`（`ENV_9999` 必须被拒绝）自然一致，无需改动用例或其验收类别。
- 宽容有明确边界，未协商的共享码不会被静默吞掉。

### 代价与待办

- **校验层严格、消费层宽容**：在枚举放宽之前，B07 的 `validate.py` 仍会拒绝带 `ANALYSIS_5002` 的 Job，而 B07 的消费路径（MDFixer 读取报告）必须容忍它。这个分层是刻意的——校验器校验的是*已协商契约*，消费端还要防运行时的意外——但需要 A07 知晓。
- 前缀归属划分；把 `error.code` 放宽为 `anyOf: [enum(共享码), pattern(^ANALYSIS_[0-9]{4}$)]`，使 A07 专有码也能通过 B07 校验器。发起前此项保持待办。
- 未知 `ANALYSIS_*` 码的语义在 B07 侧不可解释，只能原样透传给人工排查；这是刻意接受的代价。
