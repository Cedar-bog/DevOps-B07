- README 中的预期输出对「修什么」无增量信息，只影响「怎么分层」。

## 8. R1–R4 选择过程

| 规则 | 判定 | 结果 |
| --- | --- | --- |
| R1 未用过 | 通过 | 6 个候选均为首次生成，无历史构建记录 |
| R2 多数一致 | 触发，未能裁决 | 归一化分组：{error-driven-1, error-driven-2}=2；{error-driven-3, context-driven-1}=2；{context-driven-2}=1；{context-driven-3}=1。两组各 2 票并列，无唯一多数 |
| R3 关键词 | 触发，未能裁决 | 6 个候选均含 `make` 与 `build-essential`，无法用错误行核心词区分 |
| R4 LLM 裁决 | 触发 | LLM 从 6 个候选中选择 `context-driven-3`：先装编译工具、再复制源码并单独构建，依赖安装与源码复制解耦，缓存更稳定 |

R4 调用记录：`work/candidate/responses/r4-decision.json`（HTTP 200，延迟 31.63s，prompt 1372 tokens，completion 4240 tokens，其中 reasoning 4211 tokens，finish=stop）；裁决结果 `work/candidate/r4-decision-parsed.json`；完整判定链 `work/candidate/decision.json`。

最终选择：`context-driven-3`，写入 `work/candidate/Dockerfile`。

## 10. 结果与结论

- 初始 Dockerfile 复现失败（exit 1，`make: not found`）；
- 两类提示各生成 3 个合法候选，全部定位到同一根因；
- R2 出现 2:2 并列、R3 无区分度，实际走到了 R4 由 LLM 裁决——这是本论文方法中「规则无法决定时兜底」的完整路径；
- 选中候选构建成功（exit 0），容器在无网络环境下输出 `hello E3`（exit 0），与 README 预期一致；
- 结论：DRAFT 的「构建失败定位 → 两类提示生成候选 → R1–R4 选择 → 复建验证」闭环在本地 Docker 环境可复现；候选高度相似时，R2/R3 不足以裁决，R4 是必要兜底。
